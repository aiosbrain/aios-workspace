# Task synchronization protocol — task-sync/1

Status: proposed canonical supplement, draft r3 for coordinator integration and independent review. This draft implements AIO-1188's independently reviewed r3 specification. It does not advertise runtime availability, enable a project, or supersede tracker requirements. Wire schema is `tasks-sync.schema.json` (draft-07; ID `urn:aios:task-sync:1`), referring only to the pinned `urn:aios:mcp-next:1:actions` action/status/sync definitions. Revision 1.0.0 of this supplemental protocol is independent of the shipped `mcp-next/1` action envelope.

## Capability and scope

An enabled server advertises `task_sync_versions: ["task-sync/1"]` only when the transports, protected writers, persistence and lifecycle adapter are installed. A cached advertisement is a hint; every request checks live capability, member credential, project visibility and project state. No capability flag grants authorization. Existing task feeds remain byte-compatible. New clients never fall back to revisionless `/items` following a task-sync conflict/failure. The legacy proposed `mcp-next/1` Batch can only be handled by an explicit already-bound-link adapter; this draft does not permit guessing a link or baseline.

The only editable canonical fields remain title, assignee, status and due. New direct actions still use `task.create` and `task.update` with their unchanged closed `mcp-next/1` parameters. Bodies, arbitrary fields, deletion, remote provider transport and new admin MCP tools are not added.

## Transport and limits

- POST `/api/v1/tasks/reconcile`: body `Request`; response is the corresponding ConnectResult, AttachResult, BatchResult or AcknowledgeResult.
- GET `/api/v1/tasks/reconcile`: exactly one normalized Query variant; response Snapshot, Discovery, or the stored/current POST operation result. No GET mutates domain state or persists operation/receipt changes; pre-acceptance rejection is derived read-only.
- GET `/api/v1/tasks/{task_id}`: the unchanged pinned Task response; do not silently add workspace link data to it.
- The proposed existing-session-admin route POST `/api/admin/tasks/revisions` accepts AdminRequest and returns AdminResult. It is not member task-sync or an action allowlist entry. The coordinator owns route/auth integration.

Require authenticated active team-posture member credentials for task-sync operations. Delegated read tokens, anonymous credentials and external-posture mutation attempts fail. A separate task GET retains its existing member read/tier visibility rules. Revalidate destination/source/task provenance visibility at every operation, resume and acknowledgement; link possession never grants visibility.

Read request bytes incrementally with an 8,388,608-byte ceiling, fatal UTF-8 decoding and no unbounded request.json allocation. Over-ceiling is HTTP413 invalid_payload with a bounded recovery message; invalid JSON/shape is HTTP422 invalid_payload. Authentication precedes expensive parsing. Limit each authenticated credential to 30 task-sync POSTs/minute and 60 GETs/minute, plus a bounded 10,000 outstanding row intents per actor/destination; quota refusal is HTTP429 rate_limited before accepting a new operation. Existing accepted operation status/replay does not create more row intents. Draft fixture sizes never imply every legal 5,000-row maximum fits the byte ceiling; both limits apply, and clients can use independent bounded additive reconcile batches.

ID strings are opaque max128. Every protocol string excludes U+0000. Preparation generation is0 only for the initial disabled state; preparing/enabled generations are positive. Opaque tokens/cursors are max2048, bound to destination/query/generation and interpreted only by the issuing server. Array limits: reconcile rows5000, attachment selections200, snapshot/discovery page200, acknowledgement receipts5000, eligible assignees1000, statuses6, fields4, per-row field conflicts4. Complete batches can expose at most20,000 conflicts. No silent truncation of choices or conflicts. A destination with more eligible assignees than the bound returns an actionable error rather than an apparently complete list.

Raw GET syntax requires `contract_version=task-sync/1` and explicit `view=snapshot|attachable|operation`. Snapshot/attachable require link_id; operation requires project_id and operation_id. Omitted cursor normalizes to null. In attachable view, omitted row_keys normalizes to []; otherwise row_keys is a comma-separated list of exact opaque keys, at most200, encoded with URLSearchParams. Reject repeated query keys, unknown keys, duplicate row_keys and malformed/empty explicit row_keys. A view cannot accept the parameters of another view. Cursor query binding covers view/filter/link/project/member so it cannot widen a read.

Every non-success transport result is the closed TransportError shape. HTTP401 unauthorized; HTTP403 forbidden for visible disallowed operation; HTTP404 not_found for absent or unauthorized task/source/link; HTTP409 operation_id_conflict/refresh_required/invalid_generation/upgrade_required or initialization conflict before batch acceptance; HTTP422 shape or invalid value; HTTP429 limit; HTTP503 unavailable/operation_in_progress for transient pre-acceptance failure. Body messages are bounded and payload-free. Server lifecycle/business failures after durable batch acceptance are row outcomes, not a misleading transport success claim.

## Source connection

Connect identifies one destination by authenticated member/team/project, local random workspace UUID, and either an existing source item ID or a create descriptor. Existing source must be a visible task item in the same project. Create descriptor is the bounded task document payload (path/access/body/frontmatter/row observations) from the user's existing authorized publication flow; actor/kind/team/project are stamped by the server. Validate canonical workspace path, access tier and reserved path rules with shared item ingress. The source path is at most 500 Unicode code points, matching the canonical item path ceiling. Schema and source-ingress validation count supplementary characters as one code point; a JavaScript UTF-16 code-unit length check must not reject a path within this limit. Never accept admin/private, create a new project, change an existing source audience, overwrite another source kind, or invoke the legacy task materializer from connect. Frontmatter is JSON only, maximum100 properties, depth8 and64KiB serialized size within the request cap; server attribution fields cannot be overridden. Matching source path resolves its existing item identity after authorization instead of minting a duplicate. Body/rows disagreement is rejected by the existing task parsing validation before effects.

SourceRow values are raw local observations, not authority to change canonical tasks. Preserve them for explicit mapping/initialization. The source envelope uses shared item ingress validation, while the raw observations retain their task-sync bounds and must agree with the parsed document body. They are not legacy materializer rows and must not inherit its narrower assignee/status limits. They cannot bypass the later canonical field validator. Connect does not edit task fields, reassign source provenance, create tasks, project providers or mark baselines synchronized. It creates/locates only the authorized source/link and its initialization metadata, with an ID-only audit. Source persistence uses the shared item boundary and transaction (the coordinator owns this integration), with task materialization explicitly suppressed; no independent ad-hoc items writer. A lost response replays the same operation and returns the same source/link.

The unique server link binding is `(team_id, project_id, destination_source_item_id, member_id, workspace_id)`. Store explicit `(link_id,task_id)` membership with its own baseline; do not join membership solely on tasks.source_item_id. A workspace link's source item is its destination document, distinct from original task provenance. Rotation of a key for the same member does not recreate the link, but execution resumes using the original action credential fingerprint as required by the governed foundation. Another member cannot take over the link merely by knowing workspace_id/link_id.

The local journal also binds canonical Brain origin/team/project, canonical workspace root and profile generation. Root paths are never sent to Brain. A changed root/destination/grant generation selects refreshed state rather than mixing acknowledged baselines. Corrupt protected state cannot silently become a new empty workspace. The profile broker remains the only profile/grant registry.

## Discovery and attachment

Attachable discovery defaults to visible, same-project Brain-origin tasks with origin ui and original source_item_id null, excluding already-attached tasks. A provider link does not change those provenance predicates. Preserve full task visibility filtering before page selection. Other-source/source-private tasks do not become discoverable just by sharing the project. Summaries expose only ID/key/revision/four values, or bounded raw values with mapping_required when legacy conversion is unresolved; no task body or unrelated source contents. An optional exact row_keys list permits bounded collision recovery. Do not disclose hidden collisions.

Selection tokens persistently bind current member/link/project/task/revision and authorization/link generation. They grant no authority. Attachment rechecks live visibility and revision under project→task→link lock. It accepts only explicit selections from that predicate or same-operation idempotent attachments. Duplicate IDs/keys reject before any membership effects. Per-selection stale/not_found/identity_conflict/identity_backfill_required outcomes produce no task/membership/baseline effects for that selection; other valid selections may attach. baseline_required and mapping_required are attached-but-uninitialized outcomes: persist that selected membership and unresolved observation so authorized reads and explicit governed resolution can reach it, while task values and synchronized baseline remain unchanged. The response carries AttachReceipt for every submitted selection.

Attach only writes membership, initialization observations/receipt and ID-only audit. Original task ID, row key, source_item_id (including null), origin, creator, audience and all provider identity/adoption fields remain unchanged. Missing legacy row key yields identity_backfill_required. Do not mint/rename a key in attachment. Snapshot now reaches the task through explicit membership.

For absent local row, Baseline is uninitialized and values null. Produce a delivery token; after checked local insertion of the selected row and acknowledgement, establish the first synchronized baseline. Never treat the initial observation as prior agreement. If a local row appears before insertion, preserve it and refresh the same link snapshot. Do not change the accepted attach operation or detach/recreate membership. Its still-uninitialized SnapshotRow exposes an InitializationGrant; retain the raced local observation in the journal and require an explicit selected-value initialize row using that fresh grant. Normal reconcile and acknowledgement cannot silently turn the appeared row into agreement. Present equal values can use the same delivery/ack path; differing values return baseline_required with original local observation retained and no automatic overwrite. Unknown/retired assignment or other unmappable raw values return mapping_required; no null/guess substitution.

A key collision on new-row reconcile is refresh_required, never a duplicate or a silent reassignment. Client retains local input and may use exact-key authorized discovery, then explicit present-row attachment. Invisible/other-source collisions remain non-disclosing and cannot be attached by assertion. A journal binding that already names another task ID is identity_conflict requiring explicit repair. A failed/truncated discovery page never authorizes creation or deletion.

## Reconciliation and governed row execution

Canonical values: title1–500 Unicode code points containing non-whitespace; assignee eligible active member ID or null; status one of backlog/ready/in_progress/in_review/blocked/done; due a real Gregorian date0001-01-01 through9999-12-31 or null. Empty strings are not clears. Workspace cell normalization can interpret an empty/legacy em dash cell as null, but the API never does so implicitly. Canonical assignment is a member UUID; no display-name similarity or exact-label guessing. Preserve unresolved raw labels as evidence.

Validate whole request shape, unique task IDs/row keys and source/link identity before accepting a batch or writing row effects. An existing row requires the exact task/key membership, expected revision, stored baseline generation and four baseline values. A false/mismatched client baseline cannot overwrite stored agreement. The explicit initialize row described below is the sole exception to the initialized-baseline requirement. A new row carries a stable local key and four canonical values; a colliding existing key is not an upsert. Missing rows do not delete anything.

Three-way merge per field compares persisted baseline B/current Brain C/incoming W: unchanged/unchanged is no-op; only W changed accepts W; only C changed preserves C with outbound pending; equal bilateral changes converge; unequal bilateral changes preserve C and conflict evidence. Nonconflicting fields may progress independently. Before any row field effects, compare expected revision; stale revision conflicts the entire row. No timestamp arbitration. Status authoring clears raw_status. Unrelated task fields and source/provider identifiers are never rewritten by this operation.

At batch acceptance persist immutable per-row intent and one server-generated governed operation identity bound to actor/team/project/row/request digest. Canonical task.create/task.update request hashes and the private baseline/source context are tied to that intent. Use the existing governed action service, its original credential/policy checks and human approval channel; no new executable action type or self-approval. Even no-op rows submit an existing-field update so task.update policy is evaluated. A row cannot execute a different plan after approval: a revision, baseline, eligibility or authorization change requires conflict/denial and an explicit fresh operation.

Export taskConsumers and an internal executeTaskIntent(ctx,intent) domain seam. The coordinator supplies readonly Object.freeze(ctx.execution) metadata from the actual executing stored action: actionId, identityId, requestHash, credentialId and credentialFingerprint. The task consumer verifies all of these against the persisted binding, not just caller-supplied operation IDs. The composition must pass or retrieve only a verified server-owned intent binding; request parameters cannot inject one. Verify exact action type, operation ID, canonical payload hash and actor/project before using it. Ordinary direct task actions retain the closed public parameters and cannot invoke arbitrary synchronization context. All consumer database work is awaited through governed ctx.query/ctx.db, no nested transaction/global pool/authority mutation/provider network work. On successful execution, task values/revision, baseline/conflict changes, outbound intents and governed result/audit commit in that transaction.

Process rows in independent bounded transactions. Persist dispatch intent before execution; a POST retry or bounded worker can resume using the same original credential binding. Never hold a5000-row transaction or wait for network/approval with database locks. A crash after action commit but before response projection recovers the authorized stored action result; it never repeats task effects. Same batch/input replays identities and current lifecycle; changed input under same ID conflicts. Sibling successful rows remain committed while another row awaits approval or fails.

A durable queued row intent is not yet an accepted governed action. Before classifying its dispatch, recover any existing real action by the original bound operation identity, actor/team/project/destination and canonical request hash. A recovered accepted action always retains its real action ID and lifecycle, including after credential revocation; never replace it with a synthetic rejection. Only when no matching action exists may a missing, revoked or fingerprint-mismatched original persisted credential produce terminal `dispatch: rejected` with error `unauthorized` or `revoked_authorization`. Authenticate and authorize the current reader/replayer and destination before exposing that outcome. GET derives it without any write. An authorized same-actor POST replay may persist the rejection, but may never dispatch the old intent using a replacement credential. This pre-acceptance rejection changes no task, baseline, conflict or acknowledgement state and creates no action/audit identity.

## Receipts, snapshots and acknowledgement

RowReceipt has separate action and domain axes. queued/unavailable and terminal rejected have no fabricated action/audit ID. A rejected receipt has action, domain and readback null and a required non-retryable unauthorized/revoked_authorization error; it has no acknowledgement. Once accepted, action is the exact existing ActionStatus envelope. requested/running/pending_approval/denied/failed/conflict have null domain and no acknowledgement. succeeded has Domain unchanged/applied/partial_conflict. Domain partial_conflict records a real Brain commit plus remaining field conflict; it is not a failed transaction. A stale governed conflict may expose an authorized readback separately but no applied domain. Receipt task IDs must agree with successful action entity and domain; these equality checks are runtime semantic invariants beyond JSON shape.

Batch phase processing means at least one row queued/unavailable/requested/running/pending approval, and returns HTTP202. All terminal rows, including denials/conflicts and pre-acceptance rejected receipts, yield complete/HTTP200; this means finished processing, not unanimous success. Compatibility applied/conflicts arrays are projections of the authoritative rows. A partial-conflict task can appear in both; pending/denied/failed/rejected never appears as applied. Rejected-only batches are complete; a rejected receipt cannot make a batch processing when all other rows are terminal. Each submitted row gets one receipt, including no-op rows and pre-execution binding conflicts accepted as governed failure outcomes. Empty batch is complete with empty arrays and no mutation.

Snapshot membership contains source-native created tasks and explicitly attached tasks, regardless of original source_item_id. Keyset cursor is `(task_id)` scoped to link/view/filter/member and source generation, at most200 rows. complete is true exactly when no next cursor remains; pagination failure/limit is not completion. Revalidate the source membership generation before initial bootstrap can become complete; refresh on concurrent insertion/generation change. New candidates during a scan are discovered on the next authorized scan. Canonical eligible choices are project-scoped, complete (max1000 members), shared at the snapshot level; each ready row has its own permitted field list. Return mapping_required raw row form when canonical conversion is impossible; direct pinned Task GET then returns a safe mapping_required error instead of inventing a canonical member ID.

Baseline has explicit initialized/uninitialized state and generation. An uninitialized baseline has null values; it is never replaced with current values just to fit a shape. Acknowledgement tokens bind task revision, output values, allowed field mask, baseline generation, link generation, member/destination and unresolved-field mask. Tokens are opaque unguessable IDs backed by durable records, not bearer authority. They have no arbitrary time expiry: explicit generation/visibility/revocation checks invalidate them. A token cannot acknowledge conflicting fields or an unreceived revision. In initialized state it advances only agreed fields; unresolved fields retain old baseline. Initial baseline becomes initialized only once all four fields have actual acknowledged agreement; otherwise keep the initial delivery record without falsely claiming synchronized values.

Client journals the receipt/proposed output, performs checked atomic Markdown replacement against its original hash, durably records success, then acknowledges the exact written values. The server validates token/value equality and monotonic baseline generation in one transaction. Repeating a recorded acknowledgement is idempotent; a historical token never erases newer baseline/conflict/intent and otherwise returns refresh_required. Acknowledgement never edits task fields. A failed local write cannot advance acknowledgement/cursor/clean-file state. A crash between filesystem/journal/network steps replays the token/operation and preserves local input rather than pretending cross-system atomicity.

Conflict resolution is a fresh existing task.update with explicit selected values and expected revision. Record resolving action/revision, preserve unrelated conflicts, and do not advance offline recipient baselines. Choosing the already-current value explicitly resolves the initialization/field record and invalidates stale resolution attempts; ordinary unrelated no-op does not. Initialization resolution applies both in preparing and enabled links using the correct preparation/link generation guard.

## Explicit initialization selection

A SnapshotRow or AttachReceipt for a live uninitialized link baseline, including a prior successful selection awaiting actual full acknowledgement, exposes `initialization: InitializationGrant`; otherwise initialization is null. A grant is an opaque durable server-issued token bound to member/team/project/task/link, exact live initialization/delivery record and observation digest, current task revision, link generation, and either preparation generation (`scope: preparation`) or enabled-link generation (`scope: link`). It is not bearer authority. Issuing a grant never changes task values or acknowledges agreement. Disabled projects cannot issue one.

The caller selects exactly one linked task using `mode: reconcile` with a row `{kind: initialize, task_id, row_key, expected_revision, initialization_token, values}`. `values` is the complete explicitly selected canonical four-field value; there is no invented baseline. A batch containing initialize rows contains only initialize rows (maximum200); ordinary existing/new rows cannot mix with them. The existing envelope binds link_id/link_generation/source_item_id. The server validates the token, record, source, actor, project, expected revision and all selected values before accepting immutable intent. Different task/link or stale token/generation yields refresh_required without any task effect. Multiple workspaces attached to one task receive separate grants and cannot resolve or acknowledge each other's initialization through a copied token.

Each selected row becomes the same governed task.update action with the selected fields as its closed changes payload and the fresh expected_revision. Intent privately records exact initialization record/generation/token digest; the governed action request accepts no extra fields. Policy, human approval, live eligibility and original credential checks remain mandatory. Scope is frozen before approval; execution cannot silently switch from preparation to link scope, switch links, select another unresolved record or replan stale values. Approval resume verifies the complete binding plus revision and current generation under project→task→link lock. Failed/denied/pending outcomes produce no task/baseline/conflict resolution or acknowledgement effects. Succeeded produces the same per-row Domain/acknowledgement shape as normal reconciliation.

An authorized initializer applies its explicitly selected values and records selection resolution of only that selected initialization record. Selection resolution is distinct from completion: the link remains initialization-incomplete until its full four-field acknowledgement commits, and activation continues to count it as pending. Retain immutable history of every selected action/revision and create or renew the live delivery/selection record for that still-uninitialized link; snapshot continues to issue a grant bound to that current record, current task revision and current generation, even after an earlier selected action succeeded. It preserves observations and unrelated link conflicts; other links see the new Brain revision with their own baseline/initialization still unresolved. Explicit selection of existing Brain values can resolve the targeted record and produces a new resolution revision even with no changed field, preventing stale competing selections from succeeding. An uninitialized baseline stays null until all four fields are actually written/verified locally and acknowledged. A normal direct task.update may resolve initialized field conflicts but cannot infer or borrow one of these initialization grants from task ID alone. Thus the preparing exception has an explicit callable path without expanding public actions.

After an absent attachment insertion race, the already-created same-link membership remains reachable through snapshot even though attachable discovery excludes it. The client keeps the newly appeared local row untouched while it obtains that row's grant and chooses initialize values. A fresh initialization operation handles the selection; the original attach operation remains replayable with its original absent input. Local replacement still compares the observed hash. If a second local edit happens after initialization action success but before replacement, preserve that edit and do not acknowledge the delivery. Refresh snapshot to obtain the still-uninitialized link's renewed initialization grant, require another explicit full-value selection, and submit a fresh initialize operation with the newly observed revision. This recovery repeats until a checked replacement and full acknowledgement succeed; it never invents a baseline, automatically overwrites the new local values, or reuses a prior selected action as authority for changed input. No implicit membership re-observation, detach or provenance reassignment is required.

## Administrative preparation and protection

The task administrative service exports prepareTaskRevisions, activateTaskRevisions and abortTaskRevisionPreparation. It accepts a coordinator-created session-admin transaction context (not a public member action context), verifies a live instance/team administrator and exact project, then locks the project preparation row. Proposed HTTP route is POST `/api/admin/tasks/revisions` with existing session/CSRF/admin guards. No MCP tool or member API can call it. Each operation ID has a durable scoped digest/result/audit, and expected_generation compares atomically; prepare's absent initial state uses generation0.

Prepare changes disabled→preparing, establishes initial revision identities and immediately enables the protected-writer fence/legacy-provider pause. It creates explicit unresolved initialization records for unknown baselines/mappings; it cannot guess a mapping or discard values. Large backfill is resumable in bounded transactions; phase remains preparing and cannot activate until the backfill generation is complete. Response readiness counts are derived from persisted state, never optimistic estimates. Calling prepare again with the same operation ID replays; with a fresh ID/current generation it resumes an unfinished preparation without resetting previous edits or acknowledgements.

Preparing permits reads, connect/attach initialization metadata, acknowledgement and narrowly scoped governed initialization resolution. Ordinary create/reconcile field mutation remains unavailable; only the explicit initialize row variant above may enter the governed initialization exception. Initialization resolution binds a live-authorized explicit task.update to one unresolved preparation record/generation, compares revision and applies its chosen fields plus receipt/conflict resolution atomically through the same protected service. Human approval remains required where policy says so. Provider intents remain paused/pending. For enabled-link initialization, use that link's current generation instead of requiring project state preparing.

Activate is a separate administrator transaction. It locks the current project generation and verifies complete backfill, explicit identity mappings, complete current link acknowledgements, no initialization conflict/pending approval and supported or paused writers/providers. Incomplete activation returns409 preparation_incomplete without changing state. Unsupported PM-connected projects stay preparing until AIO-1189. Successful activate changes preparing→enabled and bumps generation. Abort retains preparing/protection and bumps its generation to invalidate unfinished preparation tokens/intents; it never restores unsafe disabled semantics. Resume requires refreshed state. Disabled is only the pre-protection legacy state, not a rollback target for protected rows.

Every authoritative protected writer uses project→task→link lock order, live checks and the shared writer. A database invariant backstop rejects protected field edits/deletes/downgrades outside that transaction-bound writer; the marker is internal discipline, not authority. Legacy `/items` preflight covers the materializer's entire affected project sweep before project freshness/item/version/task/link effects. Changed protected row, omitted protected row, equal-body/changed-rows, kind/path substitution and visibility-widening reclassification return409 upgrade_required. An unchanged authorized replay is a no-op and cannot advance revision/baseline. Unaffected projects retain legacy behavior. Disabling new capabilities or rollback pauses workers while retaining histories, identities and protection.
